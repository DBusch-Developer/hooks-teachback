Hooks, in plain English.

A walk through the React hooks I used to build a real project — what they are, what they do, and the actual code I wrote with them.

Project: Build-A-Beast — project tracker · React + Redux + React Router

What is a hook?

A function that lets you "hook into" React features from inside a regular function component.

Before hooks, if you wanted your component to remember things or do things when stuff changed, you had to write a class. Hooks took those features and moved them into plain functions.

The pattern

A hook is just a function whose name starts with use. You call it at the top of your component, and React keeps track of the rest.

What I'll cover

useState · useEffect — the everyday ones
useContext · useReducer — for bigger state
useRef — for DOM refs and non-state values
useMemo · useCallback — for performance
useParams · useNavigate — from React Router
useSelector · useDispatch — from React Redux
Custom hooks — write your own

Talking points

  • Hooks were added in React 16.8 (2019). Before that, anything stateful needed a class component.
  • The "use" prefix is mandatory — it's how React (and the linter) know it's a hook.
  • I'll show real code from my Build-A-Beast project for each one.
  • If anyone asks "why hooks instead of classes?" — they let you reuse stateful logic, the code is shorter, and you don't have to worry about this.

One thing before we dive in — imports

Hooks aren't global. You import them from wherever they live. Here's the cheat sheet for everything in this talk:

From React itself
import {
  useState,
  useEffect,
  useContext,
  useReducer,
  useRef,
  useMemo,
  useCallback,
  createContext
} from "react";
From libraries
// React Router
import { useParams, useNavigate }
  from "react-router-dom";

// React Redux
import { useSelector, useDispatch }
  from "react-redux";

// Your own custom hooks
import { useToggle }
  from "./hooks/useToggle";

Only import the ones you actually use in that file. If you import useEffect and never call it, the linter will complain.

useState

Lets your component remember something between renders.

You give it a starting value. It gives you back the current value plus a function to update it. When you call the update function, React re-renders the component with the new value.

import { useState } from "react";

const [value, setValue] = useState(initialValue);

What's happening
const [count, setCount] = useState(0);

// click +
setCount(count + 1);
// React re-renders, count is now 1

Same idea as the demo on the left. The number on screen is the state. Click a button, state changes, React re-paints.

From my project — login form

client/src/pages/Login.jsx 
const [loginForm, setLoginForm] = useState({ email: "", password: "" });

// inside the input...
<input
  value={loginForm.email}
  onChange={(e) =>
    setLoginForm({ ...loginForm, email: e.target.value })
  }
/>

Two things to notice: (1) the state is an object, not just a string. (2) When I update it I spread the old state first (...loginForm) so I don't wipe out the password when I'm only changing email.

From my project — modal toggle

client/src/components/NewProject.jsx 
const [showModal, setShowModal] = useState(false);

// when the user clicks the "+ New Project" button
<button onClick={() => setShowModal(!showModal)}>
  New Project
</button>
Same pattern, live
showModal: false

The trick

A boolean in state is the cleanest way to show/hide anything — modals, dropdowns, edit forms. The variable name reads like English in your JSX: {showModal && <Modal/>}.

Talking points

  • State can be anything — a number, a string, a boolean, an object, an array.
  • You never mutate state directly. loginForm.email = "x" won't trigger a re-render. You always call the setter.
  • When state is an object, spread the old state so you only update the field you want.
  • Every component that calls useState gets its own copy — two of the same component on the page have independent state.

useEffect

Lets your component do something outside of rendering — fetch data, set up a subscription, sync to something external.

Rendering should be predictable. Anything that isn't just turning state into UI — calling an API, reading from storage, navigating — goes inside useEffect.

import { useEffect } from "react";

useEffect(() => {
  // the effect
}, [dependencies]);

Three modes — based on the dependency array

no array
useEffect(() => {...})
Runs after every render. Usually a mistake — easy way to make an infinite loop.
empty []
useEffect(() => {...}, [])
Runs once, when the component first mounts. Good for initial data fetches.
[someValue]
useEffect(() => {...}, [x])
Runs on mount, then again any time x changes. Good for reacting to state.

The three effects running

  // runs every render
});

useEffect(() => {
  // runs once on mount
}, []);

useEffect(() => {
  // runs when input changes
}, [input]);

Type in the box. The log shows which effects "fired." The third one only fires when the typed value actually changes.

From my project — fetch on mount

client/src/pages/ProjectDetail.jsx 
const { projectId } = useParams();

useEffect(() => {
  dispatch(projectGetOne(projectId));
}, []);

The detail page mounts → fetch this one project's data from the backend. Empty array means "do this once and then stop."

From my project — react to a state change

client/src/pages/Login.jsx 
useEffect(() => {
  if (isLoggedIn && user.token) {
    navigate("/");
  }
}, [isLoggedIn]);

When the user submits the login form, Redux flips isLoggedIn to true. This effect notices, and sends them to the home page. Without the dependency, this would never know to run.

From my project — sync local state to Redux

client/src/components/ProjectEdit.jsx 
useEffect(() => {
  if (project.projectName !== "") {
    setProjectEdit(project);
  }
}, [project]);

When the project data loads from Redux, copy it into the local edit form state so the inputs show the current values. Then the user can edit without touching Redux until they hit save.

Talking points

  • The dependency array is the most important part. Wrong dependencies = stale data or infinite loops.
  • The linter warns if you reference something inside the effect that isn't in the deps array. Listen to it.
  • The function returned from useEffect (if you return one) runs cleanup — useful for unsubscribing, clearing timers.
  • If anyone asks about infinite loops: it happens when the effect updates state that's in its own dependency array. Update → re-render → effect runs → update → forever.

useContext

Pass data through your component tree without sending it as props at every level.

When a lot of components need the same data — the logged-in user, a theme, a language preference — you can stop drilling it through every prop and put it in a Context instead. Any component inside the Provider can grab it directly.

import { createContext, useContext } from "react";

const UserContext = createContext();

// at the top of the tree
<UserContext.Provider value={user}>
  <App />
</UserContext.Provider>

// anywhere inside
const user = useContext(UserContext);

What I actually did

In Build-A-Beast I used Redux for the logged-in user. Almost every component does this:

const { user } = useSelector((state) => state.auth);

What I could have done with Context

// in App.jsx
export const UserContext = createContext(null);

<UserContext.Provider value={user}>
  <Routes>...</Routes>
</UserContext.Provider>

// in NewProject.jsx — no more useSelector for user
const user = useContext(UserContext);

{user.roles.includes("Project Manager") && (...)}

Context vs Redux

Context is for

Stuff that rarely changes — current user, theme, language. Read-heavy, write-light. Comes with React, zero setup.

Redux is for

Lots of related state with frequent updates and async logic. Dev tools, middleware, time-travel debugging. Worth the setup for an app like Build-A-Beast.

Another example — theme toggle

This is the classic Context use case. Every styled component on every page needs to know the current theme. You'd never prop-drill theme through 40 components, and it's not really app state — it's UI configuration. Read-heavy, write-light, needed everywhere.

// ThemeContext.jsx
import { createContext, useContext, useState } from "react";

const ThemeContext = createContext();

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState("dark");
  const toggleTheme = () =>
    setTheme(t => t === "dark" ? "light" : "dark");

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

// custom hook for cleaner consumption
export function useTheme() {
  return useContext(ThemeContext);
}

Wrap the app once:

// App.jsx
<ThemeProvider>
  <Routes>...</Routes>
</ThemeProvider>

Then any component can read it or flip it:

// Navbar.jsx — the toggle button
const { theme, toggleTheme } = useTheme();

<button onClick={toggleTheme}>
  {theme === "dark" ? "☀️" : "🌙"}
</button>

// any other component, anywhere in the tree
const { theme } = useTheme();

Two things worth pointing out: the Context value can be an object with both the value and the function to change it (so consumers can read and write), and that useTheme() wrapper is a custom hook that hides the useContext boilerplate — a really common pattern you'll see in production code.

Talking points

  • The choice between Context and Redux is real — Context isn't always the wrong call, and Redux isn't always the right one.
  • Context re-renders every consumer when the value changes. For frequently-updating state that hurts.
  • You can have many Contexts in one app — UserContext, ThemeContext, LocaleContext, etc.
  • Theme is the textbook example because it's read-heavy, write-light, and needed everywhere. Perfect fit.
  • The Provider component uses useState internally — Context isn't a replacement for state, it's how you share state.
  • If anyone asks "why not always use Redux?" — Redux adds boilerplate. For a small app, Context is enough.

useReducer

Like useState, but for state with lots of moving parts.

When state gets complex — multiple fields, nested objects, related changes — useReducer moves the update logic out of your JSX and into one place. You dispatch actions and a reducer function decides how state changes.

import { useReducer } from "react";

const [state, dispatch] = useReducer(reducer, initialState);

function reducer(state, action) {
  switch (action.type) {
    case 'INCREMENT': return { ...state, count: state.count + 1 };
    case 'RESET':     return initialState;
    default:           return state;
  }
}

dispatch({ type: 'INCREMENT' });

Live demo — same counter, reducer version

0
The reducer
function reducer(state, action) {
  switch (action.type) {
    case 'INCREMENT':
      return { count: state.count + 1 };
    case 'DECREMENT':
      return { count: state.count - 1 };
    case 'RESET':
      return { count: 0 };
  }
}

What I actually did

client/src/components/NewProject.jsx

My new-project form had a giant nested state object. Every input did this:

const [project, setProject] = useState({
  projectName: "",
  projectDescription: "",
  customer: { customerName: "", customerEmail: "" },
  roles: [],
  // ...and on
});

// every onChange did this:
setProject({ ...project, projectName: e.target.value });

What I could have done with useReducer

function projectReducer(state, action) {
  switch (action.type) {
    case 'SET_FIELD':
      return { ...state, [action.field]: action.value };
    case 'SET_CUSTOMER':
      return { ...state, customer: { ...state.customer, [action.field]: action.value } };
    case 'ADD_ROLE':
      return { ...state, roles: [...state.roles, action.role] };
    case 'RESET':
      return initialProject;
    default: return state;
  }
}

const [project, dispatch] = useReducer(projectReducer, initialProject);

// in JSX
<input
  onChange={(e) => dispatch({ type: 'SET_FIELD', field: 'projectName', value: e.target.value })}
/>

All the spread-and-update logic moves into one place. JSX just says what happened, the reducer says what to do about it.

Talking points

  • If that pattern looked familiar — yes, Redux is basically useReducer scaled up to the whole app, with extra tooling.
  • Rule of thumb: if you have 3+ pieces of state that change together, consider useReducer.
  • The reducer must be pure — same input, same output, no side effects. State updates happen by returning new objects, never mutating.
  • Action objects can be anything — { type: 'X' }, { type: 'X', payload: ... }, etc. Convention is type + whatever fields you need.

useRef

Two jobs: grab a real DOM element, or hold a value that doesn't trigger re-renders.

Most of the time you want React to manage everything. But sometimes you need to talk to a DOM element directly — focus an input, scroll to a position, measure a div. useRef gives you a stable handle to it. The .current property is mutable and persists across renders.

import { useRef } from "react";

const inputRef = useRef(null);

<input ref={inputRef} />

// later
inputRef.current.focus();

Live demo — autofocus

Click the button → input gets focused

The button doesn't manage state. It just reaches in and calls .focus() on the ref.

The code
const inputRef = useRef(null);

const handleClick = () => {
  inputRef.current.focus();
};

<input ref={inputRef} />
<button onClick={handleClick}>focus</button>

What I could have done in my project

client/src/pages/Login.jsx

Auto-focus the email input when the page loads, so the user can just start typing:

const emailRef = useRef(null);

useEffect(() => {
  emailRef.current?.focus();
}, []);

<input
  ref={emailRef}
  type="email"
  value={loginForm.email}
  onChange={...}
/>

Small touch, big UX win. The same pattern works for modals — focus the first field when the new-project modal opens.

The second use — holding values without re-rendering

Refs aren't just for DOM elements. You can stick anything in .current and it persists across renders without triggering one. Useful for storing a timer ID, a previous value, or a count of something you don't want to display.

const renderCount = useRef(0);
renderCount.current++;
// changes but doesn't cause a re-render

Talking points

  • Don't use refs to do things React should do. If you're reading state from a ref or manually editing the DOM that React owns, you probably want regular state.
  • Refs are escape hatches. Use them when the React way doesn't fit.
  • The ?. in emailRef.current?.focus() is a safety check — the ref is null on the very first render before the element exists.
  • Changing .current never re-renders. That's the whole point.

useMemo

Cache the result of an expensive calculation so it doesn't re-run on every render.

Every time a component renders, all the code in it runs. Usually fine. But if you've got something slow — sorting a big list, computing aggregates, filtering thousands of items — useMemo remembers the result and only re-runs the calculation when its inputs change.

import { useMemo } from "react";

const result = useMemo(() => expensiveCalc(items), [items]);

What I actually did

client/src/pages/Tasks.jsx

I filtered projects inside the JSX every render:

{projects
  .filter((project) => project.projectName == selectedOption)
  .map((project) => (...))}

Works fine for a few projects. With a few thousand it'd be wasteful — re-filtering every time anything in the component re-renders.

What I could have done with useMemo

const filteredProjects = useMemo(
  () => projects.filter((p) => p.projectName === selectedOption),
  [projects, selectedOption]
);

{filteredProjects.map((project) => (...))}

The filter only re-runs when projects or selectedOption changes. Type in some other input on the page? Filter doesn't re-run.

Another spot — the Dashboard

client/src/pages/Dashboard.jsx

I hard-coded the dashboard numbers ($2,500,000, 44, 22). Those should come from real data:

const totalSpent = useMemo(
  () => projects.reduce((sum, p) => sum + p.budget, 0),
  [projects]
);

const ongoingTasks = useMemo(
  () => projects
    .flatMap((p) => p.tasks)
    .filter((t) => t.status === 'Ongoing').length,
  [projects]
);

Talking points

  • Don't memoize everything. Profile first. useMemo has its own overhead — it's only a win when the calculation is genuinely expensive.
  • The dependency array works just like useEffect — include every value you read inside the function.
  • Common rule: memoize computed values (sort, filter, reduce), not cheap ones (string concat, basic math).
  • If anyone asks "should I memo every array I create?" — no. React 19's compiler will handle a lot of this automatically.

useCallback

Like useMemo, but for functions instead of values.

Every render creates new function references. Usually harmless — but if you pass a function to a child that's wrapped in React.memo, the child re-renders anyway because the function "changed." useCallback keeps the same function reference between renders unless its dependencies change.

import { useCallback } from "react";

const handleClick = useCallback(() => {
  doSomething(x);
}, [x]);

What I actually did

client/src/components/ProjectEdit.jsx 
const handleDelete = () => {
  dispatch(projectDelete({ projectId, email: user.email }));
  navigate("/projects");
};

A new handleDelete function every render. Fine, because I'm not passing it to a memoized child — I'm using it on a button right there.

When it would matter

const handleDelete = useCallback(() => {
  dispatch(projectDelete({ projectId, email: user.email }));
  navigate("/projects");
}, [projectId, user.email]);

<DeleteButton onDelete={handleDelete} />
// where DeleteButton is wrapped in React.memo

Now DeleteButton only re-renders when the actual delete behavior changes, not every time something else in the parent updates.

The honest take

When to actually reach for useCallback

1. You're passing the function to a child wrapped in React.memo.
2. The function is a dependency of another hook (like useEffect) and you don't want that hook re-running every render.
3. You've measured a performance issue and traced it to function identity.

If none of those apply: don't bother. It adds cognitive cost for no benefit.

Talking points

  • useCallback(fn, deps) is just shorthand for useMemo(() => fn, deps). Same idea, different shape.
  • Most projects overuse useCallback. Wrapping every function in it isn't free.
  • Pair it with React.memo on the child or it does literally nothing.
  • Same with useMemo — these are surgical tools, not blanket "make my app faster" hooks.

Custom hooks

Extract repeated hook logic into a function you can reuse.

If you're writing the same useState + useEffect dance in multiple components, pull it into a custom hook. Custom hooks are just functions whose names start with use. They can call other hooks. They follow the same rules.

function useToggle(initial = false) {
  const [value, setValue] = useState(initial);
  const toggle = () => setValue(v => !v);
  return [value, toggle];
}

The pattern I repeat all over my project

In NewProject.jsx, ProjectEdit.jsx, NewTask.jsx, TaskEdit.jsx, and a few more, I have the same thing:

const [showModal, setShowModal] = useState(false);

// and then
<button onClick={() => setShowModal(!showModal)}>...</button>

Extracted into a custom hook

// hooks/useToggle.js
import { useState, useCallback } from "react";

export function useToggle(initial = false) {
  const [value, setValue] = useState(initial);
  const toggle = useCallback(() => setValue(v => !v), []);
  return [value, toggle, setValue];
}

// in NewProject.jsx
const [showModal, toggleModal] = useToggle(false);
<button onClick={toggleModal}>...</button>

Live demo — two toggles, one hook

Both buttons use the same useToggle logic
modal A: false

modal B: false

Each call to useToggle() creates its own independent state. Same logic, two instances.

Another candidate from my project — the form pattern

I have this pattern in every form (login, new project, edit project, new task, edit task):

const [form, setForm] = useState(initial);

const handleChange = (e) => {
  setForm({ ...form, [e.target.name]: e.target.value });
};

Could become:

function useForm(initial) {
  const [values, setValues] = useState(initial);
  const handleChange = (e) =>
    setValues(v => ({ ...v, [e.target.name]: e.target.value }));
  const reset = () => setValues(initial);
  return { values, handleChange, reset, setValues };
}

// in Login.jsx — way less code
const { values, handleChange } = useForm({ email: "", password: "" });

Talking points — this is the capstone

  • Custom hooks are how you scale React knowledge. Once you have the building blocks, you compose them into your own patterns.
  • The "use" prefix is mandatory — the linter uses it to know that the rules of hooks apply.
  • Custom hooks don't share state. Each component that calls useToggle() gets its own state. That's a feature.
  • Look at the React ecosystem — almost every library exposes custom hooks: useQuery, useForm, useNavigate. Now you know how to write your own.

Router hooks

Same hook pattern, but they come from React Router instead of React itself.

The library uses hooks to give you access to URL stuff from inside your components. Two I used a lot:

useParams — read values from the URL

client/src/pages/ProjectDetail.jsx 
import { useParams } from "react-router-dom";

// route is defined as "/projects/:projectId"
const { projectId } = useParams();

// now I can use projectId to fetch the right project
dispatch(projectGetOne(projectId));

If the URL is /projects/abc123, then projectId is the string "abc123". The route definition uses :projectId as a placeholder, and the hook pulls it out.

useNavigate — change the URL programmatically

client/src/pages/Login.jsx 
import { useNavigate } from "react-router-dom";

const navigate = useNavigate();

useEffect(() => {
  if (isLoggedIn) {
    navigate("/");
  }
}, [isLoggedIn]);

Sometimes you don't want a link — you want to send the user somewhere as a result of an action. After a successful login, after a form submits, after they delete something. navigate("/path") is the function for that.

Talking points

  • These follow the same rules as React's built-in hooks — top of the function, not inside loops or conditions.
  • useParams only works inside a component that's rendered by a Route with placeholders.
  • useNavigate replaced the older useHistory hook in React Router v6.

Redux hooks

How my components read from and write to the global store.

Redux holds shared state — stuff a bunch of components all need to see, like the logged-in user. Two hooks connect components to it:

useSelector — read from the store

client/src/App.jsx 
import { useSelector } from "react-redux";

const { isLoggedIn } = useSelector((state) => state.auth);
const { user } = useSelector((state) => state.auth);

You hand it a function that picks out the slice of state you care about. If that slice changes, your component re-renders. The whole component tree could change — you only re-render when your slice changes.

useDispatch — send actions to the store

client/src/pages/Login.jsx 
import { useDispatch } from "react-redux";

const dispatch = useDispatch();

// when the form submits
dispatch(authLogin({ ...loginForm }));

dispatch is a function. You call it with an action (here, authLogin with the form data). The action gets handled by a reducer, the store updates, and any component that's selecting that slice re-renders.

Both together — the App component

const dispatch = useDispatch();
const { user } = useSelector((state) => state.auth);

useEffect(() => {
  if (user.email !== "") {
    dispatch(projectGetMany(user.email));
  }
}, [user]);

Read the user from Redux. When the user changes (login or logout), fetch their projects. Three hooks working together: useSelector reads, useEffect watches, useDispatch writes.

Talking points

  • Redux hooks come from react-redux, the bindings library — not Redux itself.
  • You can have many useSelector calls in one component, each selecting a different slice.
  • The selector function runs after every action — keep it cheap. Don't do heavy filtering or mapping inside it.
  • If anyone asks "why not just useState?" — useState is per-component. Redux is for state that lots of components need to share.

Rules of hooks

Two rules. That's the whole list.

1

Only call hooks at the top level

Not inside loops, conditions, or nested functions. React relies on the call order to keep track of which state is which.

2

Only call hooks from React functions

From a function component, or from a custom hook (a function whose name also starts with use). Not from plain JavaScript functions.

Why?

React identifies your hooks by the order they're called. First useState = the first one. Second useState = the second one. If you put one inside an if, sometimes it's there and sometimes it isn't, and React loses track of which state goes with which call.

// 🚫 bad
if (isLoggedIn) {
  const [name, setName] = useState("");
}

// ✓ good
const [name, setName] = useState("");
if (isLoggedIn) {
  // use name here
}

Recap

  • useState — remember things between renders
  • useEffect — do things outside of rendering, react to changes
  • useContext — share data without prop drilling
  • useReducer — useState for state with multiple moving parts
  • useRef — DOM refs and values that don't trigger renders
  • useMemo — cache expensive calculations
  • useCallback — cache function references
  • useParams / useNavigate — read and change the URL
  • useSelector / useDispatch — read and write Redux state
  • Custom hooks — package your own patterns
  • All of them follow the same two rules. All of them start with use.
